# The Azure asset register — quarterly cycle

Bitpool decision, 2026-08-27, taken during the `DCF-20` control review. This file records the
architecture, the reasoning, and the procedure.

---

## 1 — Why Azure is a point-in-time dump, not a live register

Bitpool's asset inventory (ISO/IEC 27001 **A.5.9** — *"An inventory of information and other
associated assets, including owners, should be developed and maintained"*) is **federated**: each
asset class has one authoritative source, and no single tool holds everything.

| Asset class | Authoritative source | Cadence |
|---|---|---|
| AWS infrastructure | AWS resource tags | **Live** |
| Azure infrastructure | `az resource list` dump published to the wiki | **Quarterly** |
| Laptops, phones, peripherals, personnel, policies | Drata | **Live** |
| SaaS and vendors | Drata vendor register | **Live** |

Azure is the only quarterly member, for two reasons established by measurement rather than
preference:

1. **There are no tags to derive a register from.** 1 of 43 resources carried any tag on
   2026-08-27, and it was `hidden-title`. AWS, by contrast, already carried `OwnerContact`,
   `Environment`, `WorkloadType` and `Criticality` on exactly its durable instances — so tag-first
   works there and would have been net-new work here.
2. **The estate is small enough to enumerate exhaustively.** 43 resources in 14 populated resource
   groups can be listed in full on one page, which a 46,000-resource AWS estate cannot. Exhaustive
   enumeration is a stronger evidence position than a sampled or derived one.

**Do not reconcile against Drata's Azure connection.** It reported one asset of 43, last updated
2026-01-30 and untouched since. It is not a source of truth for this estate.

The URL is **not** the file path. GitBook flattens sub-folders and derives the first segment from
the `SUMMARY.md` group heading, so a page in `compliance/` publishes under `/security/compliance/`
regardless of nesting. Verified against the live wiki 2026-08-27.

Pages are written via `/bitpool-docs`, which owns `security-documentation`'s taxonomy, frontmatter
schema and index tooling. Never write them from this skill.

## 3 — The tagging standard: resource groups, not resources

14 populated resource groups against 43 resources, and the group names are already meaningful
(`Sentinel`, `code-signing-resource-group`, `veeam_data_cloud_resource_group`, `powerBI`). Tagging
at group level covers the estate for a third of the effort and survives resource churn inside a
group.

| Tag key | Required | Holds |
|---|---|---|
| `Owner` | Yes | The accountable **team**, not an individual — A.5.9's owner. Bitpool's Asset Management Policy permits "an individual or an entity" |
| `Purpose` | Yes | What the group is for, in a few words |
| `Criticality` | Yes | `critical` / `high` / `standard`, matching the AWS `Criticality` vocabulary |
| `OwnerContact` | Recommended | Current human point of contact; allowed to go stale without breaking the register |

A team-level `Owner` is deliberate: individual ownership is what left 38 assets in Drata assigned to
former staff, including three laptops. Teams survive turnover.

## 4 — The quarterly procedure

Generated by an Automation for Jira rule in the **CYB** project. Steps:

1. **Confirm the session** — `/azure-context`, then `az account show`.
2. **Produce the dump** — the collection block in `azure-querying.md` section 2, against
   `bitpool.com` / subscription `3e13a29f-90c5-40a8-abb9-8d25f5911d82`.
3. **Confirm the two Entra-only tenants are still empty** — the no-RBAC check in `/azure-context`
   section 4, against `bp-it-testing.com` and `BitpoolExternal.onmicrosoft.com`. Expect
   `count: 0`. A non-zero result means a subscription appeared and the register's scope has
   changed, which is a finding in its own right.
4. **Compare the dump to the register page.** Report three sets explicitly:
   - **New** — in the dump, absent from the register.
   - **Removed** — in the register, absent from the dump. These are decommissioned assets; record
     the removal rather than silently deleting the row.
   - **Changed** — same resource, different group, location or tags.
5. **Update tags** on any resource group that is untagged or mis-tagged against section 3.
6. **Update the register page** via `/bitpool-docs`, and stamp the dump date in its frontmatter
   `last_reviewed`.
7. **Record the comparison outcome** on the CYB ticket — even "no change" is the evidence that the
   review happened.

**Order matters at step 6 and 7.** The page is updated before the ticket closes; a closed ticket
over a stale register is the defect this cycle exists to prevent.

## 5 — What the 2026-08-27 baseline found

Recorded because a later run should know what "normal" looked like, and because several of these
were unrecorded anywhere before this review.

- **43 resources, 15 resource groups (14 populated).** `veeam_logging_group` was empty.
- **`Microsoft-Sentinel-LAWS`** — the Sentinel workspace, `pergb2018`, 90-day retention. Plus a
  second workspace, `managed-onepasswordftdn33ek-ws`, 30-day.
- **`bitpoolCodeSigningVault`** — a Key Vault holding code-signing keys, sole occupant of its group.
- **Five Sentinel incident-response playbooks** — `Block-EntraIDUser` (entity-trigger and incident
  variants), `disable_Account_On_Impossible_Travel`, `CreateIncidentFromImpossibleTravel`,
  `postToTeamsOnIncident`, plus a `teams_notification` Logic App. Live automations relevant to the
  A.5.24–A.5.28 incident-management controls.
- **`break_glass-login`** — a scheduled query rule monitoring break-glass account logins.
- **`GitProtect`** data collection endpoint and rule — repository backup telemetry into Sentinel.
- **Veeam** — `veeam_M365_And_EntraID` and `veeam_data_cloud_office_365`, backup of M365 and Entra.
- **`BitpoolExternal.onmicrosoft.com`** — the external CIAM directory, surfacing as a resource
  inside this subscription even though that tenant holds no subscription of its own.
- **Access**: three subscription Owners, and one `User Access Administrator` scoped at tenant root
  (`/`). Raised separately under privileged access; not this register's to treat.

## 6 — What this register does not cover

State these explicitly on the register page. "We checked and there is nothing" is defensible;
silence is not.

- **`bp-it-testing.com`** and **`BitpoolExternal.onmicrosoft.com`** hold no Azure subscription.
  Confirmed quarterly, expected to remain so.
- **The M365 Exchange licence subscription** in `bp-it-testing.com` is a commercial subscription,
  not an Azure resource subscription. It belongs in the SaaS and vendor lane.
- **Non-taggable Azure constructs** — Entra objects, role assignments and policy definitions are
  not returned by `az resource list` and are governed by the identity and access controls rather
  than by this register.
