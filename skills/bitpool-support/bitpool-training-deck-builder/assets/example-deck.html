Why Claude · 1 of 5

We keep rebuilding the same work.

It was never a shortage of effort. It is a shortage of reuse — the same work gets rebuilt from scratch, over and over.

AI on its own does not fix this. An empty chat still starts from zero — which is exactly why Bitpool writes the way we work into skills.
01

Your work starts from zero

The symptom
  • Every report, deck and reply begins on a blank page
  • Having to manually copy finished work into other documents
  • It's repetitive and boring
02

Knowledge sits in heads

The cost
  • How we do it properly is known by one or two people
  • New starters have to learn by asking around, slowing everyone down
  • When those people are busy, the work waits
03

Output drifts

The result
  • Two people build the same document two different ways
  • Structure, brand and level of detail all vary
  • More time is spent fixing mistakes, that could have been avoided

The best way to prompt Claude is through these three habits.

01

Give it the context

Start here
  • Say who it is for and what it is for
  • Paste or upload drafts, files or the error
02

Show it what good looks like

Set the bar
  • Hand over a finished piece you want it to match
  • Tell it what format you want it in — a table, a one-pager, an email
  • Use a skill to complete the job if one exists
03

Treat it as a conversation

Then iterate
  • Claude's first answer should always be treated as a draft response
  • If the solution doesn't look right, say what is wrong with it and ask again
  • Download context as an .md file if you want to carry a conversation across into a new chat

Memory

Claude carries context between chats, but it keeps a summary rather than a transcript. Re-state anything that has to be exact.

L

Long conversations

A long chat is summarised as it runs rather than cut off. Start a fresh one when you move on to a different job.

Where you work · 3 of 3

Changing things in Code and Design.

Both work the same way: describe the change in plain language, then review what comes back. Code changes the back end, Design changes the front end.

Talking about a change in Claude Code
  • Say where and what: "In the alarms page, default the date filter to the last 7 days"
  • Say what must stay the same, so it doesn't tidy up things you didn't ask about
  • Ask for a plan first, then review the changes before they become a commit or PR
Talking about a change in Claude Design
  • Point or circle the exact thing: "Make this card heading smaller and cyan"
  • Change one thing at a time, look at it, then ask for the next tweak
  • When it looks right, hand the build to Claude Code to make it real
Asking Claude Code and Design for changes — walkthrough.

Why it exists

A skill on your laptop helps you. Sharing it helps everyone.

A skill sitting on your laptop only ever helps you. In the shared space it helps everyone — and it keeps getting better instead of going stale.

01

One source of truth

Find it once
  • One place to look, for everybody
  • No competing copies with slightly different rules
  • If it is not in there, it is not the current version
02

Improvements compound

Fix once, for all
  • A fix you make is a fix for the whole team
  • Problems get logged and repaired instead of worked around
  • The catalogue on the wiki stays in step with the repo
03

Reviewable and reversible

Safe to change
  • Changes arrive as pull requests, not as surprises
  • Full history — you can see what changed and why
  • Retired skills are archived rather than deleted
Same reasoning as Git for code — skills are instructions we all depend on, so they get versioned, reviewed and shared rather than passed around.

How it goes
  • Asks questions until the idea is clear, then draws a flow chart for your yes

Changes a mod that already exists.

How it goes
  • Asks which mod, and what should change

3.0

Puts a mod from the Mods folder onto your machine.

How it goes
  • Lists the available mods if you don't name one

  • Can take a mod off again, putting things back as they were
